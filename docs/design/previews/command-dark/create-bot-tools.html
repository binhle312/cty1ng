CS4b · Step 4 · One Tools list with badgesApprovedOne Tools list. Each tool has a badge: Internal (run by this app) or the provider name (Anthropic, run on its servers); a tool both can do has both badges. Order: Internal only, then both, then provider only; inside each group, by the date the tool was added to the catalog (oldest first). Internal tools are on by default, provider tools off. One switch per tool. Each row says what the tool does, what it costs and what changes when it is off. Rows with an amber ⚠ can send data out of the app. Rule for development (your ask, 01:44): when the provider already has a tool for a job, we use it and do not build our own yet. Needs a decision (spec PR): code execution changes "bots never run code"; MCP connector opens a channel out of the app that D53 assumes does not exist; the switches are bot settings (migration).

CS4c · Step 4 · A tool both can doApprovedLater, a repo author can add an internal tool for a job that a provider tool already does. Example: our own Web fetch next to Anthropic Web fetch. The author maps the pair in the tool catalog (both tools get the same job name). The list then shows one row for the job with both badges, placed after the Internal-only tools, and a choice: Off · Internal · Anthropic. Only one is on: option 2, chosen by you (01:55). The bot never gets two tools for one job in a run.
