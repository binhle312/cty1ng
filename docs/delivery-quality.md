## 1. Counting rules

| Measure | Definition |
| --- | --- |
| Issue | A confirmed actionable defect, contract difference, test gap, or process failure. Keep its type explicit. Suggestions and new feature requests are separate. |
| Unique issues | Count distinct issue IDs after duplicate reports are reconciled. The same defect in several comments or review rounds counts once. |
| New occurrence | A different affected path or a defect introduced by a repair gets a new issue ID. Link its shared cause and, when known, the repair that introduced it. |
| Reopened issue | Reuse the original ID when its repair did not resolve the same defect. Record a reopen event; do not count another unique issue. |
| Severity | Copy the recorded priority, such as P1 or P2, and its source. Use `unknown` when the source does not assign it. |
| Review round | One completed review of a stated revision and scope. Multiple comments in that review are one round. A follow-up review is another round. |
| First-review findings | Unique confirmed issues first found in the first completed independent review. Later discoveries remain separate. |
| Escaped issue | An issue first found after the introducing PR merged. Attribute it to that PR only with evidence; name the discovery PR separately. |
| Fix-induced issue | A new defect caused by a prior repair, supported by a source or reproduction. Link the parent issue or repair. |
| Open issues | Confirmed unique issues whose state is `open` or `partial` at the recorded cutoff. |
| Dropped issue | State `dropped`: a confirmed issue the owner decided not to fix, with the owner's reason and date. It counts in unique issues and not in open issues. |
| Closed issue | State `fixed` with verification evidence, or `withdrawn` with a reason. A commit, merged PR, or applied lesson alone does not prove closure. |
| Unknown | Evidence is absent or incomplete. It is never zero. |
| Zero | A complete review or reconciled ledger explicitly supports no occurrences in the stated scope. |

A lesson can describe several issues; several lessons can describe the same issue.
Lesson counts are source coverage, not defect counts.
Keep estimates and partial review snapshots separate from exact unique totals.
An itemized count is a known subset; it is not the total for a PR or milestone.
Do not add snapshots with uncertain overlap.

## 7. Update and assess

1. At the creation of a PR in a milestone or an audit, add its milestone and source coverage to
   the [PR register](delivery-quality-register.md#3-pr-register).
   A PR whose findings all get ledger rows has the coverage `Ledger`.
   A PR with no milestone needs no entry (`AGENTS.md` §9; owner, 2026-11-11).
2. For a PR in a milestone or an audit, add the round after each review. Reconcile its findings
   with existing issue IDs. A PR with no milestone keeps its review rounds in its description
   (owner, 2026-11-24). It also keeps each review finding there, open or fixed, in the
   `Defect and review fixes` table. The line holds the fix, or the decision that leaves the finding
   open, and the "Same cause" answer with its search; the finding gets no issue row (owner,
   2026-11-25). A finding that the PR leaves open is also a row in the follow-up list of
   `docs/status.md`. A rule that gives a review finding a ledger row or issue row is for a PR in a
   milestone or an audit. The review guide checks the "Same cause" answer of each line of that
   table, as of a row.
3. After a fix, add the verification result and change the issue state only when evidence supports it.
4. After a new discovery, check whether it escaped a merge, repeats a cause, or came from a repair. Record the general rule and the search of old fixes ([bug fix, step 2](workflows/bug-fix.md)).
5. At PR handoff, after the merge of `origin/main`, run `pnpm records:counts --write`. It writes
   the rows it owns in the [milestone view](delivery-quality-register.md#2-milestone-view) and
   the count cells of each `Ledger` row of the register from the rows of the ledger files.
   CI runs `pnpm records:counts` and fails when a count is stale. Its
   list of ledger files is `LEDGER_FILES` in `scripts/records-counts.ts`: a PR that moves rows to a
   new file adds the file there, and the check fails until it does.
6. At milestone close, confirm the PR population in [register §2](delivery-quality-register.md#2-milestone-view).
   Calculate the totals from distinct IDs in this file and the archive.
   Then move the rows with the state `fixed`, `dropped` or `withdrawn`, and the round rows of merged
   PRs, to the [archive](delivery-quality-archive.md), unchanged, in a PR that changes records only.
   A `withdrawn` row stays out of the confirmed totals there too.
   Do the same move before that time if `wc -c` gives more than 80,000 bytes for this file. If no
   row can move, or if the file is not below 80,000 bytes after a move, ask the owner and do not
   move again (owner, 2026-11-11).
   A script shows that each moved row has no change and that the counts stay the same (owner,
   2026-11-24).
7. Add one row to the [prevention actions](delivery-quality-prevention.md#prevention-actions)
   for a recurring cause. Include an owner and verification evidence.

The builder maintains this file in the delivery change. The reviewer checks that each row of the
PR is true: its state, commit, test and source. A count that `pnpm records:counts` writes is not a
finding: CI checks it (owner, 2026-11-18, q4 Q3 A).
Quality changes must preserve the scope of existing approvals.
