## Merge effect check

**Approved contract.** Plan line 87 requires the effect check for the exact granted merge. It must hold if auto-deletion or a release triggered by the merge can happen, or if it cannot rule those effects out. Line 116 gives `MERGE_EFFECT_UNCLEAR` for an effect the tool cannot establish and keeps separate codes for bad reads and ineligible merges. Lines 27–31 also reserve indirect release and deletion for the owner. Order 149 authorizes the separately checked cleanup step after a merge. It does not authorize deletion as a side effect of the merge. [Plan line 87](../plan-b/plan.md#code-design-and-state) · [Refusal codes](../plan-b/plan.md#refusal-codes) · [Order 149](../../docs/plans/pr-140-overnight-cleanup.md#decision).

**Current behavior.** `before_merge` reads the live PR and checks the granted head and base, eligibility, the base repository's auto-delete setting and merge method. It lists the base repository's current workflows and repository hooks. Anything outside the three known disabled workflow states, or a hook whose `active` is not `false`, holds the merge. A denied or invalid hook read can hold it too. The code never reads the workflow definitions or the reviewed change to them. CI validation runs after this check. The checkout contains `ci.yml`, `codeql.yml` and `security-review.yml`. Opus reports active workflows. This pass verified the files and the check, and did not verify live activation or live hook permissions for this identity. Fine-grained credentials require repository Webhooks read permission for the hook list. [Merge preflight](../../.agents/skills/overnight/scripts/night.py#L299) · [GitHub webhook list permissions](https://docs.github.com/en/rest/repos/webhooks#list-repository-webhooks).

**Both observations hold.** With active ordinary CI, the inventory rule refuses a normal PR even if CI cannot release. With empty current lists, the rule permits a PR that introduces a release on `push` to `main`. The in-memory probe confirmed those preflight decisions. It did not run a real merge or workflow. GitHub also supports merge-related `pull_request` and `pull_request_target` close events, and downstream calls or runs. Current workflow names cannot determine those effects. [GitHub workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) · [Workflow syntax and filters](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).

**Proposed behavior.** The preflight makes one decision for the exact repository, PR, reviewed head, base revision and method. Use complete, revision-bound evidence for the event paths that can run when the PR merges and for their known downstream effects. Include the effective workflow content after integration. Account for new, edited, moved and deleted definitions, and changes to called workflows, actions and scripts where they can change an effect. Account for merge events, branch and path filters, `workflow_run`, reusable workflow calls and applicable external automation. A label like “CI” or “release” is insufficient. Use owner-approved evidence of the capabilities of known CI and other automation, with release capability outside the approved ordinary CI scope. Do not infer safety from missing access, a partial listing, a mutable dependency or an unknown receiver. [GitHub called workflows](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows) · [GitHub automation security](https://docs.github.com/en/actions/reference/security/secure-use).

For this draft, prefer a bounded repository policy. Keep the approved CI and external automation evidence in a chief or owner-controlled source. A PR cannot approve its own automation. Let approved CI run when the proposed merge preserves its known capabilities. Send any new or changed release trigger to **Needs you**, including the first release workflow or creation through a rename or downstream path. Also send an unknown effect to the owner. Under the bounded policy, changes to automation outside the approved scope need owner review even if they may be harmless. Check auto-delete for the actual head repository or hold fork merges until the rule is proved. Read and test the fork-specific GitHub behavior before claiming it. Record the relevant setting, ref, automation evidence and reason for an owner handoff. Revalidate if the evidence or reviewed revisions move. The plan limits the atomic GitHub guard to the PR head. External policy and base reads still have a race, so the design should use owner-controlled policy and state that limit. [GitHub automatic branch deletion](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-the-automatic-deletion-of-branches).

Acceptance examples for the proposal:

- A ready app PR changes no release input and preserves approved ordinary CI. With auto-delete off, green required checks and a valid grant, it sends one pinned merge request even with active CI.
- A PR adds a release workflow on `push` to `main`, changes an existing release trigger, or enables publishing through an existing workflow's dependency. Each holds before a merge attempt and names the trigger or unknown effect.
- An unchanged release bound to an event the merge cannot cause, with complete evidence, does not stop ordinary CI. An unresolved hook, workflow read, or fork auto-delete setting holds the operation.
- A scoped positive control uses approved active workflows. Named breaks remove the proposed workflow comparison, ignore downstream or external effects, ignore auto-delete, accept an unknown effect, and reject the safe active-CI control. Use fake API responses first. The approved daytime checks still need their own evidence.
